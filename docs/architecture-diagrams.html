系统架构说明

Reading-English-Web：
整体流程图与时序图

四个子项目串成一条流水线 —— 采集服务把新闻变成「素材梗概」，生成服务把梗概变成「双语泛读短文」， 两者写入 Supabase 的两张表，学生前端只拿 publishable 密钥读已发布文章。 下面按「组件拓扑 → 两条内部流程 → 端到端时序」三层拆开。

  • 4子项目，一条流水线
  • 2张业务表 + RLS 隔离
  • 74条单元测试全绿
  • 31步端到端时序

一、组件拓扑与数据流

实线是控制流，虚线是调用本机 LLM。绿色标签是写入/读出的数据表。 注意两条写入路径都指向同一个数据底座，而前端只以 anon 身份读取 —— 这是整个系统的权限核心。

二、素材采集流程

采集服务 :8020 —— 检索 → 清洗 → 梗概 → 查重 → 入库。任何一环不满足条件都会停下来告诉管理员，而不是硬塞进素材库。

三、语篇生成流程

生成服务 :8010 —— 扩写 → 自检 → 重写闭环 → 预览 → 人工确认 → 入库。代码管可确定的项，LLM 管语义项，两者都过才允许入库。

回炉闭环：任一自检不通过 → 把具体问题（缺多少词、哪段编造了事实、哪段中英没对上）回喂给模型重写， 最多 4 次重写、共 5 轮；多个候选里挑「问题最少 + 词数最贴近区间中值」的那一版。 自检仍不过时 commit 会返回 422 拦住入库，除非管理员显式 force=true。

四、端到端时序图

三段：管理员采集入库 → 管理员生成入库 → 学生阅读。实心箭头是请求，虚线是返回， 竖条是参与者的活跃区间。小屏可左右滑动查看。

五、五个关键机制

素材查重：两重判据

梗概指纹
sha256(归一化梗概)，忽略全部空白差异
来源链接
忽略 http/https、www. 前缀、末尾斜杠、# 锚点；保留查询串
为何两重
同一篇报道抓两次，LLM 两次梗概措辞有微差 → 指纹不同
命中后果
返回 409，阻断入库

生成校验：分工

代码判定
词数区间、中英段落数一致、段落数在区间内、中文段落无残留英文
LLM 判定
是否编造事实、是否含敏感内容、是否真的互为翻译
词数区间
L1 80–120 / L2 120–180 / L3 180–240
计数口径
以代码计数为准，模型自报词数只作参考
长度约束
给「每段几句」而不是「每段几词」——9B 模型数不准词数
事实清单
梗概拆成事实句并按段派活，编造空间被压到最小
回炉闭环
反馈里点名「你写了 N 段、差 M 词」并附上一版原文，最多重写 4 次

检索兜底：双通道

主通道
SearXNG 元搜索，串行 + 限流，总预算 45 秒
兜底通道
白名单媒体 RSS 直采，同一套过滤与排序规则
触发条件
SearXNG 有响应但候选为空（验证码 / 超时 / JS 壳）
排序
全局相关度排序 + 每源配额，避免单频道刷屏
去重
URL + 标题两把键，同一报道被多频道推送只留一条

段落绑定与只读

绑定规则
english_paras[i] ↔ chinese_paras[i] 一一对应，数量必须相等
前端交互
选中一侧 → 另一侧对应段落高亮（双向）
只读保证
前端只有 publishable 密钥，RLS 层禁写
收藏
只存 localStorage 快照，换浏览器即丢失

幂等与启停

种子数据
seed.sql 包在 DO 守卫里，可重复执行不插重复文章
停服务
杀进程树 + 按端口兜底，避免留下占端口的孤儿进程
起服务
启动前清端口，启动后逐个探活并点名失败项
脚本编码
.ps1 存为带 BOM 的 UTF-8，PS 5.1 与 7 都能跑
配套脚本：scripts/e2e_smoke.py（端到端冒烟）、scripts/probe_material.py（单条素材复跑）、 scripts/probe_themes.py（四主题检索耗时与区分度）、 scripts/start.ps1 / stop.ps1 / status.ps1。 交互接口见 :8010/docs 与 :8020/docs。
